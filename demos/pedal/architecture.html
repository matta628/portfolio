Architectureguitar-pedal-cpp

A software guitar pedal on a Raspberry Pi 5: a USB interface hands the audio thread 256 frames of guitar every 5.33 ms, a C++ chain of up to ten effect stages processes them in place, and the same buffer goes back out to the interface's headphone jack. Around that one callback sit a footswitch and LEDs on the GPIO header, a looper with a WAV store, 38 presets with saved edits, and a dependency-free web server that serves the pedal's own bench console. Everything on this page was read off the code at commit c53a85f and off the Pi itself over ssh, not off the README, which is behind the code in several places (section 10). Numbers are a snapshot taken on 14 September 2026.

1 · One callback, one deadline

The constraint everything else is arranged around.

RtAudio opens one duplex stream on the interface (src/main.cpp, open_stream) and calls audio_callback once per buffer. The default is 256 frames, and the sample rate is negotiated against what the device advertises with 48 kHz preferred (audiodev::pick_rate), so the budget is 256 / 48000 = 5.33 ms. Miss it and ALSA plays a gap; Telemetry counts that as an xrun. The whole per-buffer job is one function, run_block, so the same code path can be driven by the sound card or by the built-in signal generator when no interface is plugged in.

The rules inside run_block are the ones any real-time audio thread lives by: no allocation, no locks, no syscalls. They show up as concrete decisions rather than a comment. The mono scratch buffer is sized after openStream reports the buffer size it actually granted and before startStream lets a callback run; a buffer larger than that is answered with silence and an xrun rather than a resize. Every control the other threads can touch is a relaxed atomic the callback reads once at the top of the block: the preset index, the knob values, the looper's trigger / clear / seek flags, the freeze capture flag, the master level. steady_clock::now() is called twice per block for the timing figure, which on Linux is a vDSO read, not a syscall.

The order in the top lane matters. Freeze sits after the board so a captured chord already has the preset's colour on it, and the looper sits last so it records what you would hear. A master level comes after even the looper because it is a room control, not a tone control, and it survives preset changes where a preset's trim does not. The mono result is fanned out to both channels of the interface in the callback itself: asking RtAudio for a one-channel output stream puts the guitar in one ear and silence in the other, which was a bug that shipped once.

2 · The Pedalboard and its sixteen stages

One instance of everything, for the life of the process.

Every effect implements one interface, Effect::process(float* buffer, size_t n_frames) (include/Effect.h is nine lines). The Pedalboard owns exactly one instance of each of sixteen stages as plain members, and a preset is nothing more than an ordered array of up to ten Effect* into those members plus a list of (parameter index, value) pairs. Pedalboard::select() applies the values through the stages' atomic setters, stores the trim, then publishes one integer; process() does one relaxed load of that integer and walks the array. Switching presets therefore constructs, frees, resizes and reorders nothing, which is what makes it safe to drive from the footswitch thread and the browser at the same time while the callback is mid-buffer. The price is a rule the table has to obey: because stages are shared, a preset must set every parameter of every stage it uses, or the sound depends on which preset was selected before. offline_tests enforces that (test_every_preset_fully_specifies_the_stages_it_uses).

Biquad (include/Biquad.h) is the shared building block under Tone, Amp and EnvFilter: one Direct Form I second-order section with the RBJ cookbook formulas for low shelf, peaking, high shelf and lowpass. DF1 was chosen because coefficients change while the filter is running (a knob moves) and DF1 tolerates that where DF2 does not. Coefficients are recomputed only when a cached knob value differs from the last one used, so the transcendentals run on the block after a knob moves and on no other. Two things live outside the board on purpose: Freeze, a performance control that must work on every preset rather than a tone stage that would silently do nothing on the presets whose chain omits it, and the Looper, section 3.

The 70 board knobs plus six appended in main.cpp (master level, three freeze controls, two looper controls) make 76 parameters, each described once as an id, group, label, range, getter and setter. The web UI renders that table generically and never learns what a reverb is; adding a stage changes Pedalboard.cpp and Presets.cpp and nothing in the server or the page.

3 · Looper, Freeze, and the loop store

Two ways to hold sound, and where the takes go.

The Looper is a state machine, Empty → Recording → Playing ⇄ Overdubbing, that only ever changes state on the audio thread at the top of process(). on_trigger(), clear(), seek() and set_paused() from any other thread set a flag and return. Its buffer is allocated once at construction, 120 s by default (about 23 MB of mono float at 48 kHz), because the callback may not grow it later. Two details are there to keep saving and loading real-time-safe: snapshot() refuses while Recording or Overdubbing, the only states in which the callback writes the buffer, so the web thread never copies from under a writer; and load() copies the samples into a spare buffer on the web thread and the callback then swaps the two vectors, a pointer exchange that neither allocates nor memcpys up to 23 MB inside a 5 ms window. Overdub writes back existing × decay + input, scaled by decay only and never by the monitor level, so turning the loop down cannot erase it a pass at a time.

The change that made the demo possible. Normally the looper is last, so it records the finished tone. Since ea810f1 (12 Sep 2026) the chain has a second order, chosen with --clean-loop on the command line or POST /api/looper?action=clean from the page: the looper moves to the front of run_block, records the untouched input, and its playback joins the live signal before the board. One dry take can then be heard through every preset, which is what the demo's re-amp player relies on and why the four demo loops are the store's "dry" takes. The cost is stated in the code: Freeze then lands after the looper, so a frozen pad is no longer captured into the loop.

Freeze is a spectral hold, not a grain looper. Capture takes a 4096-point FFT of the last moment (with a second, overlapping frame to measure each bin's true phase advance), keeps the magnitudes, and resynthesises every 1024 samples with fresh phase, overlap-added. Nothing is replayed, so nothing can repeat; a looped 300 ms grain would re-trigger the pick attack three times a second. Shimmer sets how random the phase is, decay whether the pad holds forever or fades. With one footswitch the browser picks whether a stomp drives the looper or the freeze; a freeze press captures on the press edge, and a hold over 400 ms releases on the way up, so tap = latch and hold = momentary without costing the press any latency.

LoopStore writes mono 16-bit PCM WAV, so a take is worth something outside this program. Names arrive from a browser and become paths, so anything outside [A-Za-z0-9 _-] is dropped and the result capped at 64 characters; a file is written as .part and renamed, so a crash cannot leave a half-file that lists as a loop; duplicate() is a byte copy under a derived free name and never overwrites. Loading a loop recorded at a different rate is refused rather than resampled, because playing 44.1 kHz through a 48 kHz stream shifts it up about a tone. This is the store on the Pi on 14 Sep 2026:

4 · Presets, edits, notes, stats, setlist

What the pedal remembers, and in which file.

src/Presets.cpp is data, not mechanism: 38 presets as a table of id, name, a ten-character LCD name, a blurb, the gear being approximated, a chain of stage ids and a settings list built by per-stage helpers that cannot be called with a value missing. Two are defaults (Clean, Custom Amp), twelve are attempts at specific records (Slowdive, Elliott Smith, The Strokes, Arctic Monkeys, The Voidz, Wednesday, Led Zeppelin, Deftones, Velvet Underground, Cocteau Twins, Nirvana, Radiohead — Radiohead's is the longest chain at seven stages), and 24 isolate one effect or one trick so a fault can be heard on its own. build_presets() resolves every setting to a parameter index at startup and throws on a typo, so a misnamed knob is a startup failure with a name in it rather than a slider that quietly does nothing.

Each preset carries a measured output trim, applied after the whole chain because the saturating stages are level-dependent and trimming their input would change their sound. The table spans 0.120 (Cocteau Twins) to 2.951 (Detune), 27.8 dB, produced by tools/preset_levels (section 7) and checked by a test that every preset has one.

Edits are stored as a diff against the table, not a replacement: select() applies the defaults first and the overrides on top, so a preset that gains a knob in a later build still gets a sane value for it, and "revert" is a deletion rather than a second table of remembered values. A note is deliberately not an edit; writing one does not make the UI claim the preset was modified. The file is plain text so it diffs in git and can be fixed over ssh when something was saved unlistenable, and a block for a preset that no longer exists is skipped rather than fatal.

PresetStats is the one per-preset record the callback writes: a fixed vector of atomic slots, one per preset, bumped with the block's peaks and clip count that record_block had already computed. The CSV it produces exists because a preset can be quietly unusable, loud enough that an ordinary pick attack clips, and remembering which of 38 did that is not something a person does. Setlist exists because cycling 38 presets by foot is unusable; it is written by the web thread, advanced by the footswitch thread, and never touched by the audio thread, which is why a plain mutex is fine there.

GpioButton polls its line every 5 ms on its own thread and reports a press only after the value has been stable for 20 ms; it also reports the release with the debounced hold duration, which is what the freeze's tap-versus-hold decision reads. The looper press fires on the press edge and always will, because the instant the foot lands is the loop boundary. That is exactly why gestures that need a timeout (ClickDetector, a 350 ms double-click window) were only ever put on the utility switch, where being 350 ms late to clear a loop is inaudible. The class is still in the tree and tested; rewiring it is one make_unique and one set_handlers in main.cpp.

LedPattern is pure logic: a steady base (off / solid / blink) plus a one-shot burst that overrides it, evaluated by value(now). No GPIO, no timer thread per LED, and the blink timing is offline-testable. One indicator thread wakes every 20 ms, evaluates both patterns, pushes them at the two GpioLeds (which only issue an ioctl when the value changes) and rewrites the LCD's two rows, LOOP: PLAY and FX: RADIOHED, only when the text moved. Lcd1602 never reads the busy flag; every operation waits out the datasheet's worst case, hundreds of microseconds a call, which is why it lives on that thread and could never live in the callback. The same two strings go into every state frame, so the browser shows what the panel would show on a board with no panel.

6 · Telemetry and the web server

How the audio thread is observed without ever waiting on an observer.

Telemetry is the only surface the callback writes for anyone else, and everything it writes is a relaxed atomic store into a preallocated member: input and output peak (instant attack, ~300 ms release) and RMS (~150 ms), block count, xruns, output samples at or above 0.999, and the last / average / worst block time in µs against a budget of frames / rate. The one item too big for an atomic is the 2048-sample waveform window (about 43 ms at 48 kHz, a few cycles of a low E). It uses a seqlock: the writer bumps a counter to odd, copies both windows, bumps it to even, and never waits; the reader tries up to four times and otherwise skips a UI frame. A stalled reader costs a dropped frame; a stalled writer would cost a glitch, so the asymmetry runs the right way. test_telemetry_scope_is_never_torn hammers it from two threads.

WebServer is 744 lines: one thread, one poll() loop, an eventfd so stop() does not wait out a poll timeout, and no HTTP or JSON library. Small state is pushed as a server-sent-events frame every 40 ms to every subscriber, and only built at all if someone is subscribed; the bulkier waveform is pulled by the page as raw little-endian float32, every fourth sample of the window (512 points, 4 KB), so a slow client throttles itself. Commands travel as query strings, never bodies. Limits exist for the reason the header comment gives: a runaway client must not be able to march the process into EMFILE and spin a thread at 100 % on a board whose whole job is meeting an audio deadline. Requests over 64 KB, output buffers over 1 MB (a backgrounded tab that stops draining its stream) and a 33rd connection are all dropped. The log keeps 200 entries and sends the newest twelve per frame.

9 · This demo is the same code with the sound card swapped out

What is compiled, what is stood in for, and the one line that had to change.

The page behind the "← Pedal" link is web/index.html from the pedal repo, copied at build time with three edits that build.sh refuses to apply unless each matches exactly once. Everything that makes sound is the pedal's own C++, compiled unmodified from ~/guitar-pedal-cpp/src with Emscripten into a standalone WebAssembly module; the only new C++ is engine/engine.cpp, which replaces what main.cpp does on the Pi (build the chain, run one block of it) and swaps the sound card for a re-amp player.

  • Real: the sixteen stages, the presets and their trims, Freeze, the Looper state machine, Telemetry's meters and scope, the knob table the page renders, and the 25 Hz / 15 Hz update rates. The browser's AudioWorklet hands over 128 frames at a time where the Pi hands over 256.
  • Stood in for: the web server (shim.js intercepts fetch and EventSource for /api/* and answers the same JSON shapes), the loop store and the settings file (kept in memory for one visit), GPIO, the LCD, and the sound card. The gpio block of every state frame reports nothing wired.
  • Measured differently: browsers give the audio thread no high-resolution clock, so the engine's own block timing would read as noise. A second copy of the same module runs on the main thread, mirrors every preset and knob change, and every half second times 40 blocks of the test signal; that is the Deadline panel's number, and it is a real measurement of what one block costs on your CPU.
  • The one workaround: Presets.cpp has a local helper merge(Settings, Rest...) whose std::vector arguments make argument-dependent lookup find std::merge too. GCC on the Pi accepts it; clang/libc++, which Emscripten uses, calls it ambiguous. engine/presets_prelude.h is force-included for that one translation unit and renames the helper with a macro after the standard headers are already in. The real fix is a rename in the pedal repo, which is public and is not modified from here.

The four loops the demo offers are the store's "dry" takes, recorded after the clean-loop change so the effects you switch on are doing the work you hear. They arrive as the same WAV bytes, decoded by the browser (resampled if the context is not at 48 kHz) and copied into the engine's re-amp buffer.

10 · Where the README is behind the code

Read the code; the README is an older snapshot.

  • 34 presets, 14 stages. The table has 38 presets and the board has 16 stages (the README's list omits Wave Folder and Env Filter, and its preset count predates the four filter and folder presets). Several code comments still say 34 or 36 as well.
  • 116 assertions. 185 on 14 Sep 2026.
  • Six routes. WebServer.h's header comment; there are nineteen.
  • ALSA/JACK. The I/O layer is RtAudio 6 over ALSA; nothing in the tree uses JACK.
  • Milestone 1 unchecked. The clean passthrough exists as the Clean preset and as audio_check thru.
  • Milestone 8 "nothing is wired". The looper switch on GPIO17 and the LED on GPIO22 have been wired and tested since 31 Aug; the LCD is the part still open.
  • Not mentioned at all: Freeze, the clean-loop order, the loop store, pause and seek, notes, the setlist, PresetStats and the trim table, all of which post-date the README's last edit on 31 Aug.

Architecture

The scanner is one Python process on a Raspberry Pi. Every five minutes it asks StreetEasy’s own GraphQL API for rentals matching a saved search, works out which results it has not seen, prices each new one by transit commute to two places and by what is within a few blocks, and emails the survivors ranked by total commute. Its only interface is email, in both directions: the mailbox that receives the alerts is polled for replies, and a reply in plain English is turned by Claude into a change to the search that takes effect on the next cycle, without a restart. Everything on this page was read off the code at commit bb5dc2e and off the Pi on 14 September 2026, not off a README.

Python 3.13 · curl_cffi · schedule · PyYAML · anthropic · Google Distance Matrix + Places · Gmail SMTP/IMAP · systemd Raspberry Pi 5, 2 GB as of commit bb5dc2e snapshot 14 Sep 2026

Not running today. It ran 4–14 April 2026 and 22–27 August 2026. The systemd unit has been masked (a symlink to /dev/null) since 27 August 2026 at 17:29 EDT, the same minute as the last line in its log, and the Pi’s ops notes record that as a decision rather than a fault. Nothing below is live: the numbers are what the stored state and the log say.

1 · One process, two timers

What src/main.py does, and when.

Startup sets up a rotating file log, emails an admin “Scanner started” alert, runs the email check and one poll cycle immediately, then registers two jobs with the schedule library — check_email_commands() every 30 seconds and run_cycle() every poll_interval_seconds (300 in the config) — and loops on run_pending() with a one-second sleep. There is one thread. A reply that asks for a resend runs the entire fetch-enrich-send path inline on the 30-second timer, and the poll waits for it.

The config is re-read from disk at the top of every cycle. That is the whole mechanism behind “reply to change the search”: the reply reader rewrites config.yaml, and the next cycle picks it up. Only the poll interval is read once, at startup.

2 · The poll cycle

Nine steps, in this order, every 300 seconds.

The order is about cost. Google is called in two phases with the cheap filters between them (commit b1b2259, 6 Apr): the two commute calls come first, the commute caps and the move-in window run on the result, and only listings that survive pay for the four Places calls. Everything a step needs from a previous cycle lives in a JSON file next to the code, so a restart loses nothing but the time.

Brand new versus backlog. store.py keeps the timestamp of the last successful poll. An unseen listing found within an hour of it “just appeared”; one found after a longer gap (a crash, a block, a restart) could have been up for days, so it goes in a separate Backlog section with a [BACKLOG!] subject tag instead of pretending to be fresh. Every id the API returned is remembered, not only the notified ones — a listing that failed the commute cap is never re-evaluated either.

Ranking. filters.rank() sorts by office seconds plus home seconds, shortest first; #1 in every email is the easiest place to get to and from. It also computes a score — price closeness 0.5, preferred neighbourhood 0.3, washer-dryer 0.2 — but that only orders the tail of listings Google could not route. The email footer, “Ranked by price & neighborhood preference”, describes the score and is out of date.

3 · Getting listings out of StreetEasy

There is no public API. The scanner uses the one the website uses.

scraper.py POSTs a single GraphQL query, searchRentals(input: SearchRentalsInput!), to api-v6.streeteasy.com — the same query the site’s own search results page sends, which is what the apollographql-client-name: srp-frontend-service header declares. It asks for id, area name, availability date, bedroom and full/half bathroom counts, the geo-point, price, status, street, unit and URL path, on both organic and featured edges, plus matchedAmenities, which is how washer-dryer is detected. Filters go in the request: area ids, price and bedroom bounds, a bathrooms lower bound, required and optional amenity codes. It asks for 500 results on one page, sorted RECOMMENDED; the search never returned more than 359. A 429 skips the cycle; any other failure raises, and the cycle turns that into an admin alert email.

The query and the header set were lifted from a friend’s scraper, kept in the checkout under friend_scraper_repo/: a Node Discord bot that polls the same endpoint into SQLite. It is gitignored, never imported and never run. Two of its headers are what got the Pi blocked.

4 · Enrichment, its cache and its budget

Six Google calls per new listing, and the two files that keep that number small.

Commute. Two Distance Matrix requests per listing, mode=transit, origin the listing’s geo-point, destination a configured address string. The office leg carries an arrival_time of the next weekday at half past the configured hour, so it is the actual morning commute rather than whatever transit looked like when the scan happened to run; the home leg has no arrival time. Both the display text (“42 mins”) and the seconds are kept, one for the email and one for the caps and the ranking.

Nearby. Four Places Nearby Search requests — bar, restaurant, supermarket, gym — within radius_meters, ranked by prominence, dropped below min_rating, the first N of each kept with a haversine distance from the listing. The email shows ratings for bars and restaurants and not for supermarkets and gyms.

When the counter refuses, the enrichment loop breaks and the remaining listings go on without commute data: they pass the caps (a missing leg passes) and land at the bottom of the ranking. The cap was never reached again after the cache landed.

One thing to know before deploying it fresh: enricher.py imports plain requests, which left requirements.txt when the scraper moved to curl_cffi. Both venvs still have requests 2.32.3 installed from before, so it works; a clean pip install -r requirements.txt would not.

5 · Replies are the control plane

Every 30 seconds, email_commands.py reads the inbox the alerts were sent from.

It logs in over IMAP with the same address and app password the notifier uses, searches UNSEEN, and for each message: skips and marks read anything with [Scanner] in the subject (its own admin alerts and their replies); skips but leaves unread anything from an address outside the listing and admin recipient lists; takes the first text/plain part, or tag-stripped HTML; and cuts the body at the first quoted-reply marker. Three admin-only words are matched by regex with no model call: status (last poll, seen count, the current search), logs (a tail of the log file, up to 500 lines) and restart, which replies and then calls os._exit(1) so that the unit’s Restart=on-failure brings the process back.

Everything else goes to Claude — claude-haiku-4-5-20251001, max_tokens 2048, a system prompt listing the valid StreetEasy amenity codes, and a user message that is the current search (area ids resolved to names) as JSON followed by the email body. It returns {intent, command, changes}, pulled out of the reply by a brace-counting extractor because the model does not always return bare JSON.

The area map. Neighbourhood names have to become StreetEasy’s numeric area ids. neighborhood_map.py fetches the full areas list (id, name, level, parent) from api-internal.streeteasy.com and caches it as neighborhood_map.json: 349 areas, fetched on 4 April and not since. Before the second Claude call, the command’s words are substring-matched against area names and the currently configured areas are added, so the model sees ten to twenty candidates instead of 350; a “set to…” command sends the whole list. neighborhoods.py is also the original command-line tool for the same job, still runnable.

Usage. Eleven Claude-classified commands in the scanner’s life — five resends, two queries, two config changes, two mixed — all between 4 and 6 April 2026, while it was being built, and four seen-list clears. The reply thread in the demo inbox is a reconstruction; the real reply wording is the table above.

The August loop. Two minutes after the second run started on 22 August, the first unread message it found was another project’s daily digest — the job tracker mails the same inbox, from an authorised address. Its body matched the admin status regex, so the scanner replied with a status summary. A reply keeps the incoming subject and is sent from an address that is itself authorised, and the summary begins with the word “Scanner status” — so the reply came back as a new unread command. One reply per 30-second tick, 545 in all, until 05:08 on 23 August when Gmail answered 550 5.4.5 Daily user sending limit exceeded. The loop guard added in April (a47efd7) recognises the scanner’s own mail by the [Scanner] subject prefix, which admin replies do not carry. The scanner then ran normally for four more days; the masking on the 27th is recorded as a separate decision.

6 · Running it on the Pi

What runs where, what talks to what, and what is on disk.

The unit. systemd/streeteasy-scanner.service is a system-level unit that runs venv/bin/python src/main.py from the checkout as an ordinary user, after network-online.target, with Restart=on-failure and a 30-second delay, output to the journal under its own identifier, and a 200 MB memory ceiling. The emailed restart command depends on that restart policy: it exits non-zero on purpose. The Pi’s venv is Python 3.13.5; the laptop’s is 3.12.4.

Config and secrets. Two YAML files, deep-merged at load with the second winning. config.yaml holds the search itself — price, bedroom and bathroom bounds, area ids, amenity lists, the two commute caps, the move-in window — plus ranking preferences, the notification host, port, sender and recipient lists, the poll interval, and the enrichment block: the two destination addresses, the arrival hour, the Places radius, rating floor and per-type counts, and the daily call cap. secrets.yaml holds four values: the Gmail app password, the Anthropic key, the Google key, and a StreetEasy cookie string nothing has read since 13 April. config.yaml is committed and secrets.yaml is gitignored, which is why the repository is private permanently — the search describes where someone lives and works. This page describes the fields; none of the values appear anywhere in the portfolio.

7 · What is legacy, unused, or not quite true

Found while checking the code against itself and the log.

  • The cookie era. secrets.yaml on the Pi still carries a streeteasy.cookies string. Nothing has read it since e6ab68e; the config loader has no StreetEasy section at all.
  • friend_scraper_repo/. Present on disk, gitignored, not imported. Its Discord bot, SQLite store and 30-second interval have nothing to do with this scanner; only the query text and headers were borrowed, and two of the headers had to be un-borrowed.
  • Dead methods. Enricher.enrich() (the one-shot combination of the two phases) has no callers. NeighborhoodMap.find(), .search() and .neighborhood_level_areas() have none either, and the last compares level to the string "neighborhood" while the cached map’s levels are the integers 0 to 5, so it could never return anything.
  • An undeclared dependency. enricher.py needs requests; requirements.txt no longer lists it (section 4).
  • Two stale sentences in the product. The alert footer says the listings are ranked by price and neighbourhood preference; they are ranked by commute. And the reply to a config change promises “a fresh backlog of current listings”, but the clear happens minutes after the last poll, so the re-send arrives labelled Just Posted: the backlog label is only ever used after a real gap.
  • The loop guard. Section 5. Skipping subjects that contain [Scanner] covers admin alerts and not admin replies, and the sending address is also an authorised sender.
  • The area map does not refresh itself. Only the command-line tool’s --refresh flag re-fetches it. Any neighbourhood StreetEasy has added since 4 April is unknown to the reply reader.
  • The footprint file is slightly wrong. .pi-footprint.toml calls the project “a polling script, not a standing service”. It has a systemd unit — a masked one.
  • Round-tripping the config. Every emailed change rewrites config.yaml with yaml.dump. Key order survives; comments do not.

8 · This demo

Why the inbox next door is hand-made, and what in it is real.

The scanner has no UI; its emails are the product. But a real alert lists exact addresses with two commute times each, and two dozen of those triangulate a home and an office. The config would do it in one line. So the demo is bespoke by design, and the portfolio’s publish step refuses to emit anything if a file named config.yaml is in the tree.

fuzz.py starts from one real alert (5 April 2026, kept outside the repository), parses the plain-text body, and rewrites it: addresses keep the street and lose the number to the block (“22xx”, or “56-xx” in Queens) and lose the unit; both commute times are replaced by transit-looking estimates from public neighbourhood centroids to a fictional home and a fictional office (a linear function of distance plus a deterministic jitter); the listings are re-ranked by the fictional total, the same rule rank() uses, and dealt into eight daily emails of five or six, never two units of one building in the same email. The script fails if any real address string survives into listings.json. Prices, sizes, dates, washer-dryer and the nearby bars, restaurants, supermarkets and gyms are public listing data and are left as they were.

index.html rebuilds each email’s HTML from the same inline-styled template as notifier.py, with the office leg labelled generically. The reply thread is written for the demo, and the pinned note is the pitch. What the demo cannot show is everything above that is not a listing: the backlog section, the admin alerts, the status and log replies, and two weeks of 403s.
